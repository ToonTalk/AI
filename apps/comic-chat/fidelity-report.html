Three Fidelity Fixes

A live character preview, a rebuilt balloon geometry, and a change to how characters are composited so their necks stopped vanishing. Two of the three were prompted by feedback from David Kurlander, who led the original Comic Chat project at Microsoft Research.

All three share a shape worth naming up front: in each case the port was already approximately right, and the remaining error was invisible to me but obvious to someone who knew the original. Each fix came from reading the released 1996–98 source rather than from taste, and each replaced something I had invented with something the program actually did.

1. The BodyCam character preview

The original UI pairs the emotion wheel with a live picture of your own character, which updates as you turn the dial. The port shipped the wheel without it for a slightly embarrassing reason: I had ported the wheel out of a file called bodycam.cpp and read the name as a quirk. It isn't. The widget genuinely is a camera pointed at your body, and the wheel is only its lower half.

The source says so unambiguously. The body region is the control's client rectangle with the wheel's square subtracted from the bottom:

void CBodyCam::GetBodyRect(RECT &rect) inline {
    GetClientRect(&rect);
    rect.bottom -= m_bullSide;      // subtract out bullseye
}

So the preview sits directly above the dial in one control, and CBodyCam::DrawBody fills that region white before drawing. Two details there are load-bearing. First, the body is drawn with the nimbus suppressed — body->DrawBody(&memDC, rect2, FALSE) — because the preview sits on white paper and needs no halo to separate it from a backdrop. Second, the drawing rectangle is deliberately widened by a thousand units on each side, with the reason stated in a comment: so character remains a fixed height, clipped to width. The character is scaled to fill the available height and simply cropped if it is too wide, so a tall thin alien and a broad caveman appear at a consistent scale rather than being squeezed to fit a box.

The port reproduces that sizing rule and the white ground. It shows the pose that will actually be sent, which means it obeys the same precedence the message pipeline uses: an explicit wheel setting wins for one message, and otherwise the text-analysis rules decide. A practical consequence is that typing "Hello there" makes your character begin waving before you press Send, because the greeting rule has already fired.

One deliberate deviation: the original stacks the preview above the wheel because its BodyCam lives in a tall right-hand sidebar. This port's composer is a horizontal bar across the bottom, where stacking would have cost about 130 pixels of comic strip. The preview therefore sits beside the wheel at the same size. The layout differs; the sizing and drawing rules do not.

2. Rewriting the balloon geometry

the balloons seem a little sharp / angular, and don't reproduce Woodring's cloud-like balloons exactly right, and sometime a balloon tail overlaps another balloon — David Kurlander

That is two separate defects in one sentence, and they had different causes.

The wrong kind of spline

Both implementations start from the same control points: the text block's edges, inset by a border and then given a hand-drawn wobble of ±70 twips every 300 twips along each edge. Those constants are the original's (HWAVEHEIGHT, HWAVEINTERVAL). What differed was the curve drawn through them.

The original builds its outline with a β-spline (CreateBalloonSpline, class CBeta) — an approximating curve, where control points pull the curve toward them without lying on it. I had used an interpolating curve, a midpoint-quadratic that passes exactly through every control point. That single distinction is the whole complaint: an interpolating curve visits every wobble at full amplitude and produces scallops with visible corners between them, while an approximating curve smooths the same wobbles into soft lobes. It was the difference between tracing the bumps and being suggested by them.

The fix is a closed uniform cubic B-spline over the identical control points, converted span-by-span to Bézier segments so it can be expressed as an SVG path:

b0 = (p0 + 4·p1 + p2) / 6        b1 = (2·p1 + p2) / 3
b2 = (p1 + 2·p2) / 3             b3 = (p1 + 4·p2 + p3) / 6

Nothing about the wobble changed — same amplitude, same interval, same seeded randomness in the balloon widths. Only the interpretation of the points changed, and the balloons became clouds.

The tail, and an inverted clamp

The tail was rebuilt at the same time. I had been drawing a straight triangle spliced into the outline; the original draws two opposing arcs (CArc) bulging in opposite directions by 5% of the tail's length, painted over the balloon so their white fill opens a gap in the border at the mouth. That gentle S-flare is part of what reads as "hand-drawn".

The overlap complaint had a sharper cause. When a tail would be shallower than 45° from vertical, the original clamps it — by sliding the mouth along the balloon's bottom edge while the apex stays pinned on the speaker. I had implemented the clamp backwards: I pinned the mouth and swung the apex sideways. Swinging the apex is precisely the motion that walks a tail tip across a neighbouring balloon. The bug was not a missing collision check; it was a correct rule applied to the wrong end of the line.

Two follow-on collisions

Fixing the outline exposed two related problems, because the new lobes swing wider than the old scallops did.

Stacked balloons kissed. Balloons stack with a 90-twip gap between their layout rectangles — the original's TOPBORDER + YBORDER + HWAVEHEIGHT. But the rectangle is only the spline's control frame: the rendered curve bulges up to 70 twips beyond it on each facing edge, plus stroke width. Two stacked balloons could therefore intrude on each other by roughly 100 twips while their rectangles never touched. The stacking gap now accounts for the neighbour's bump as well as its own; the measured rectangle gap is 188 twips.

Tails still grazed balloons. The original reserves a corridor at least 300 twips wide for each tail (QueryRouteRgn) so tails can never cross. But the protected point is the speaker's anchor with no margin, so a later balloon could legally sit flush against it — and then the tail's arc bulge and the neighbour's wobble both swung into the gap. Two changes: placement pads the protected anchor by 340 twips, and rendering samples the tail arcs against every sibling balloon and escalates if it finds contact, from normal bulge to straight to dropping the mouth directly beneath the speaker. The arc bulge is also capped at 120 twips, since 5% of a panel-spanning tail produced sweeping curves the original's short tails never exhibited.

Rather than trust one re-render, this was fuzzed: 120 randomly generated strips yielding 70 multi-balloon panels, sampling each rendered tail's actual path geometry against every sibling cloud, plus cloud-against-cloud checks with the wobble inflation included. Zero intersections of either kind.

3. Halos first, or: where the necks went

the heads are separated from the bodies (you should render both the head and body halos / outline masks, before rendering the head and body) — David Kurlander

Characters in the original are paper dolls: a head image and a torso image stored separately, composed at draw time by an offset carried in the art (head origin = torso.cx + face.cxDelta − face.cx, likewise in y). Each pose also carries a white aura — a halo that keeps a scratchy character legible against a scratchy engraved backdrop.

My extraction had baked each pose's aura into that pose's own image. It looked correct in isolation and was wrong in combination: when the head composited over the torso, the head's opaque white halo stamped over the torso's artwork around the neck, erasing whatever line work was there. On Anna it deleted the collar stroke of her turtleneck, which reads exactly as a head floating slightly free of its body.

The client never has this problem because it draws in a different order. Per the blit sequence in bodycam.cpp, it lays down the aura planes first with MERGEPAINT (which is dst = ~src | dst, so an aura bit paints opaque white), and only then the masks and images. Every halo is therefore already on the paper before any ink arrives, and a halo can never erase artwork — only backdrop.

The fix was to re-extract all 31 characters with the aura as a separate layer per pose, and to emit both halos before either image. The counts:

Poses extracted557 across 31 characters
Poses carrying an aura layer526
Poses without one31 — exactly the one icon per character, which has no aura offset in the file format
Artwork bundle1.9 MB → 2.4 MB

An unexpected finding

Splitting the layers turned up something none of us would have predicted: for roughly half the poses, the aura plane is pixel-identical to the mask. Faces almost always carry a genuine fringe extending past the silhouette, but for many characters the torso halo comes instead from the mask itself being drawn dilated beyond the ink outline. The halo is thus produced by two different mechanisms in the same art set, and a port that treated the aura plane as the whole story would silently lose the halo on those characters. The aura is always a superset of the mask, so drawing all halos first can never leave a gap between halo and ink.

Whether the dilated-mask torsos were a deliberate authoring choice or a by-product of the avatar editor is an open question, and one only the original team could answer.

What the three have in common

Every one of these was a case where the port produced plausible output from incorrect internals, and no amount of looking at my own screen would have revealed it. The BodyCam was missing because I mis-read a file name. The balloons were angular because I chose an interpolating curve where the original approximates, and tails wandered because I applied a real rule to the wrong endpoint. The necks vanished because I flattened a layered compositing model into a single image at the wrong stage of the pipeline.

In each case the corrective information already existed in the released source; the reason it went unused is that I did not know to look for it until someone who remembered the program said the output looked slightly off. That is a strong argument for the value of releasing source alongside software, and a stronger one for asking the people who built the thing.
